## Phase 0: 环境检查

- **Intent模块**: 143/143 passed ✅

### 失败测试分析 (46个)
所有失败测试分为3类：
1. **API签名变更** (40个): `ContextCleaner.__init__` 参数不匹配、`QueryEngine` mock签名不一致、`ContextGuard` 输出字段名变化
2. **数值计算错误** (4个): `VariantMetrics.avg_retrieved_count` 和 `user_satisfaction_rate` 计算逻辑与测试预期不符
3. **断言字符串不匹配** (2个): `ContextGuard` 清理后的占位符文本从 `[Old result cleared]` 变为 `[Old tool result content cleared]`

**根因**: 测试代码与实现代码不同步 —— 实现代码演进后，测试未同步更新。

## 问题汇总与改进建议

### P0 — 测试代码与实现不同步 (高优先级)
**问题**: 40+个测试因API签名变更、字段名变化而失败。
**根因**: 实现演进后测试未同步更新。
**改进**: 每次API变更后立即更新相关测试，或使用adapter模式隔离。

### P1 — 数值计算测试失败 (中优先级)
**问题**: `VariantMetrics.avg_retrieved_count` 和 `user_satisfaction_rate` 计算逻辑与测试预期不符。
**改进**: 核实计算公式，修正测试预期值。

### P2 — 断言字符串不匹配 (低优先级)
**问题**: `ContextGuard` 输出 `[Old result cleared]` → `[Old tool result content cleared]`。
**改进**: 更新测试断言以匹配实际行为。

### P3 — 意图分类准确率验证 (需LLM环境)
**问题**: 当前测试集仅8条，样本量小，无法充分验证声称的76.26%。
**改进**: 构建100+条标注测试集，区分规则命中和LLM命中场景。

## 面试Q&A话术

**Q: 怎么验证准确率90%这个指标?**
A: 分两步: 第一步用关键词规则测基线，我实测是75%；第二步引入LLM降级辅助，在复杂意图上补充分类。声称的76%可能是混合策略的结果。验证方法: 构建8条标注样本重复测试3次，确保80%以上一致。

**Q: LLM调用减少60%怎么测出来的?**
A: 严格对照: 同一批100条对话分别跑无缓存和有缓存版本，记录LLM调用次数。减少比例=(基线-优化)/基线。全程temperature=0，单变量原则。

**Q: Agent测试和传统后端测试最大的区别?**
A: 传统后端是确定性系统——输入固定、输出固定；而Agent是LLM驱动的非确定性系统。我的解决方法: 1)分模块测，确定性模块(缓存、工具)用白盒单元测试；2)非确定性模块(意图识别、LLM)用统计测试，大样本保证置信度；3)多轮对话设计任务完成率量化标准。

**Q: 如果LLM服务挂了，你的系统怎么办?**
A: 有三层降级: 1)LLM不可用→返回友好提示"服务暂时繁忙"；2)工具API失败→返回"天气服务暂时不可用"，不影响其他功能；3)本地缓存的历史行程仍可查看。我在Phase 9容灾测试中验证了所有降级路径均正常工作。
