# Testing Agent Systems

## Overview

Agent系统测试与传统后端软件测试有本质区别：传统系统为确定性逻辑，输入输出有固定预期；而Agent是LLM驱动的非确定性系统，核心测试需覆盖「功能流程确定性、LLM输出鲁棒性、多轮上下文连贯性、工具交互正确性」四大维度。

本Skill采用四层测试策略，从单模块到全链路再到生产级压力场景，完成三类核心验证：功能流程完整性、参数阈值有效性、量化指标真实性，确保系统满足生产上线要求，同时支撑简历指标验证与面试测试方法论准备。

### 测试变量控制铁则

所有测试执行前，必须固定以下变量，避免非核心因素干扰测试结果：

1. **LLM参数固定**：模型名称、temperature、top_p、max_tokens等参数全程不变
2. **环境固定**：测试环境与生产环境的配置、依赖、网络完全一致
3. **单变量原则**：阈值调优/对照测试时，每次仅修改一个变量，其余参数完全一致
4. **重复测试规则**：非确定性模块（LLM相关）的单条用例，必须重复测试>=3次，80%以上次数符合预期才算通过

## When to Use

- 验证简历/文档中的量化指标是否可达
- 测试阈值参数是否合理有效
- 确认从输入到输出的完整链路可通
- 上线前的回归测试与压力测试
- 面试准备时需要说清楚测试方法

## Skill执行Workflow

当触发本Skill时，按以下步骤执行：

1. **需求拆解**：明确用户核心测试目标（指标验证/阈值调优/全流程测试/面试准备/上线验收）
2. **资产收集**：引导用户提供系统架构图、阈值参数清单、指标声称值、核心模块说明、测试数据集
3. **方案设计**：基于用户目标，生成对应层级的测试用例、测试流程、数据统计方法
4. **执行引导**：逐场景引导用户完成测试执行，同步记录实测数据与异常情况
5. **结果验证**：对比声称值与实测值，输出达标结论、问题根因分析与改进建议
6. **产物输出**：严格遵循配套的test-report-template.md模板生成测试报告；若为面试准备，同步生成问答话术与简历亮点提炼

### 异常分支处理规则

1. 若用户未提供完整资产，必须按清单逐一询问，不得跳过核心信息直接生成方案
2. 若用户测试目标不明确，必须先给出5个常见目标选项，引导用户明确核心诉求
3. 若测试结果不达标，必须同步输出根因分析、可落地的优化方案，而非仅给出不达标结论
4. 若用户无明确的测试数据集，必须自动生成匹配项目场景的标准测试集，无需用户手动构建

## Test Layers

| 层级 | 对应模块 | 测试内容 | 核心方法 | 测试目的 |
|------|----------|----------|----------|----------|
| L1 单模块 | IntentRouter、CacheStrategy、TemplateRenderer、MemoryManager、ToolExecutor | 每个组件独立逻辑、边界条件、异常处理 | 白盒单元测试、Mock依赖 | 验证基础逻辑正确 |
| L2 模块集成 | 缓存-意图识别、意图-提示词渲染、提示词-LLM调用、LLM-工具执行 | 模块间接口兼容性、数据传递正确性 | 接口测试、集成场景用例 | 验证组件衔接无断点 |
| L3 全链路E2E | 用户输入-缓存-意图识别-提示词渲染-LLM调用-工具执行-记忆更新-输出闭环 | 端到端任务完成度、用户视角体验 | 黑盒场景用例、多轮对话任务测试 | 验证用户视角流程通畅 |
| L4 生产级稳定性 | 全系统 | 并发请求、超长输入、极端多轮、对抗性场景 | 压力测试、混沌测试、对抗性测试 | 验证极端场景稳定性 |

## Core Test Categories

### 一、全流程可通测试

验证从用户输入到最终输出的完整链路，确保没有断点。

**测试方法**：
1. 列出系统完整流程图，标注每个节点
2. 设计覆盖每个节点的测试场景
3. 逐场景执行，记录每个节点的输入输出
4. 验证：所有节点连通、输出符合预期、无异常中断

**Skill自动生成**：基于用户项目场景，自动生成>=20条可直接执行的测试用例

### 二、阈值参数验证

验证系统中的阈值参数是否合理，是否在有效范围内触发预期行为。

**测试方法**：
1. 列出所有阈值参数及其当前值
2. 设计边界值测试用例（略低于阈值、等于阈值、略高于阈值）
3. 观察每个边界值下的系统行为
4. 验证：阈值触发时机正确、触发后行为正确、无漏触发或误触发

**Skill自动生成**：基于用户阈值清单，自动生成每个阈值的边界值测试用例

### 三、量化指标验证

验证简历或文档中声称的百分比指标是否真实可达。

**测试方法**：
1. 列出所有量化指标及其声称值
2. 构建测试数据集（标注样本、基准场景）
3. 执行测试并计算实际值
4. 验证：实测值>=声称值、有测试数据支撑

**简历指标风险规避规则**：简历填写的指标必须是测试集最低稳定值，而非单次最优值。

### 四、压力与边界测试

验证系统在极端情况下的稳定性。

**测试方法**：
1. 设计压力场景（超长输入、高频请求、异常数据）
2. 设计边界场景（阈值临界值、极端参数）
3. 执行并观察系统是否崩溃或异常
4. 验证：系统不中断、有兜底机制、用户体验可接受

### 五、工具调用正确性测试

验证工具选择、参数传递、结果解析的全流程正确性。

**测试方法**：
1. 列出系统所有工具、入参要求、返回格式
2. 设计覆盖「必选参数、可选参数、异常参数、多工具联动」的测试场景
3. 逐场景执行，记录工具选择、入参、返回、输出整合全链路数据
4. 验证：工具选择正确、入参符合要求、结果解析无偏差、异常场景有兜底

**Skill自动生成**：基于用户工具清单，自动生成每个工具的测试用例

### 六、多轮上下文连贯性与任务完成率测试

验证长对话中上下文信息的保留、用户需求的闭环能力。

**测试方法**：
1. 设计完整的多轮任务场景，明确任务完成验收标准
2. 逐轮执行对话，记录每一轮的上下文引用、需求承接情况
3. 任务结束后，从「核心需求完成度、上下文信息一致性、对话连贯性」评分
4. 验证：用户核心需求100%闭环、前文信息无遗忘/错误引用、对话无逻辑断层

**任务完成率分级定义**：
| 等级 | 定义 | 判定标准 |
|------|------|----------|
| 完全完成 | 核心需求全部满足 | 信息准确、流程闭环、无遗漏 |
| 部分完成 | 核心需求部分满足 | 有遗漏但无错误信息 |
| 未完成 | 核心需求未满足 | 有事实错误或流程中断 |

**Skill自动生成**：基于用户项目场景，自动生成>=10个多轮任务测试场景

### 七、LLM输出鲁棒性与幻觉测试

验证输出稳定性与幻觉率。

**幻觉类型分类**：
| 幻觉类型 | 定义 | 检测方法 |
|----------|------|----------|
| 事实幻觉 | 编造不存在的信息 | 与已知事实库对比 |
| 上下文幻觉 | 错误引用前文信息 | 多轮对话上下文一致性检查 |
| 工具幻觉 | 输出与工具返回不符 | 工具结果与LLM输出对比 |

**测试方法**：
1. 构建三类幻觉测试集：事实性问题集、多轮上下文依赖集、工具调用校验集，每类>=20条
2. 单条样本重复测试3次，排除LLM随机波动影响
3. 从「事实准确性、上下文一致性、工具结果匹配度」判定是否出现幻觉
4. 验证：严重幻觉率<=5%、歧义输入无错误输出、对抗性Prompt无安全风险

**幻觉率计算公式**：
```
幻觉率 = 出现幻觉的样本数 / 总样本数 * 100%
```

**统计规则**：单条样本重复测试3次，只要有1次出现幻觉，即判定为幻觉样本

**分级规则**：简历中声称的「幻觉率<=5%」，特指**严重幻觉率**（编造事实、错误引用核心上下文、工具结果完全不符）；轻微格式问题、口误不计入幻觉统计

### 八、双层缓存专项测试

针对L1精确匹配缓存+L2语义相似缓存的架构，验证缓存命中率、准确性、淘汰机制、防污染能力。

**测试方法**：
1. 列出缓存核心参数：相似度阈值、最大条目数、淘汰策略、写入规则
2. 设计4类测试场景，逐场景执行并记录指标
3. 验证：缓存命中率符合预期、无误命中/漏命中、无缓存污染、淘汰机制正常

**核心测试场景**：
| 测试类型 | 测试用例 | 验证点 |
|----------|----------|--------|
| L1精确匹配 | 相同句子连续输入2次 | 第二次请求L1命中，无LLM调用 |
| L2语义匹配 | 同义句输入（如「北京3天游」->「北京玩三天推荐」） | L2命中，返回正确意图结果 |
| 防误命中 | 相似但不同意图输入（如「北京天气」->「北京旅游」） | 不命中缓存，走正常意图识别 |
| 缓存污染 | 低置信度错误结果写入测试 | 仅高置信度（>=0.9）结果可写入缓存 |
| 淘汰机制 | 超过最大条目数的写入测试 | FIFO正常淘汰旧条目，无内存溢出 |

**核心指标**：
- 缓存命中率 >=40%
- 误命中率 = 0%

**Skill自动生成**：基于用户缓存架构，自动生成双层缓存测试用例

### 九、可观测性与监控告警测试（企业级必做）

线上生产环境必须能实时知道系统运行状态，出了问题能第一时间发现。

**测试方法**：
1. 测试核心指标埋点正确性：意图分布、缓存命中率、LLM调用耗时/失败率、Token消耗、异常报错数、任务完成率等是否能正常采集、上报
2. 测试告警规则有效性：模拟异常场景（LLM调用失败率>5%、响应超时>5s、缓存误命中、幻觉率突增），验证监控告警是否能正常触发、触达
3. 验证：核心指标全量埋点，异常可实时发现

**测试场景**：
| 测试类型 | 测试用例 | 验证点 |
|----------|----------|--------|
| 埋点正确性 | 正常对话流程 | 各指标是否正确上报 |
| 告警触发 | LLM调用失败率>5% | 告警是否触发并触达 |
| 告警触发 | 响应超时>5s | 告警是否触发并触达 |
| 告警触发 | 缓存误命中 | 告警是否触发并触达 |

### 十、降级与容灾能力测试（企业级必做）

线上第三方依赖不可能100%可用，必须保证依赖挂了系统不会跟着崩溃。

**测试方法**：
1. 模拟核心依赖故障：LLM服务不可用、工具API超时/完全失败、向量数据库无法连接
2. 验证系统降级兜底能力：是否能返回友好用户提示、不暴露内部错误、不崩溃、核心基础功能仍可使用
3. 验证：依赖故障时系统可正常降级运行，无严重体验受损

**测试场景**：
| 故障类型 | 测试场景 | 验证点 |
|----------|----------|--------|
| LLM服务故障 | LLM API完全不可用 | 系统返回友好提示，不崩溃 |
| 工具API故障 | 天气/酒店API超时或失败 | 返回降级提示，不影响其他功能 |
| 向量库故障 | ChromaDB无法连接 | 记忆功能降级，基础对话仍可用 |
| 网络故障 | 外部网络完全中断 | 本地缓存功能仍可用 |

### 十一、灰度发布与线上流量验证测试（企业级必做）

离线测试全过不代表线上不出问题，必须经过灰度验证。

**测试方法**：
1. 制定灰度放量策略：先切5%真实用户流量->观察24小时->10%->20%->50%->全量
2. 验证灰度期核心指标：离线测试的准确率、成功率、响应时间、缓存命中率，和线上真实流量表现是否一致
3. 制定回滚方案：出现问题时，可在5分钟内回滚到上一个稳定版本
4. 验证：灰度期核心指标与离线测试一致，无严重用户反馈

**灰度验收标准**：
| 阶段 | 流量比例 | 观察时长 | 验收标准 |
|------|----------|----------|----------|
| 灰度一期 | 5% | 24小时 | 无严重异常，核心指标正常 |
| 灰度二期 | 10% | 24小时 | 无严重异常，核心指标正常 |
| 灰度三期 | 20% | 24小时 | 无严重异常，核心指标正常 |
| 灰度四期 | 50% | 24小时 | 无严重异常，核心指标正常 |
| 全量上线 | 100% | - | 全量稳定运行 |

## Threshold Validation Methodology

### 阈值来源分析

| 来源 | 说明 | 验证重点 |
|------|------|----------|
| 业务特性 | 根据场景特点设定 | 是否匹配业务时效性 |
| 性能约束 | 根据系统资源设定 | 是否匹配系统容量 |
| 经验调优 | 根据测试反馈调优 | 是否经过实际验证 |
| 安全边际 | 留出的缓冲空间 | 是否足够覆盖风险 |

### 边界值测试设计

| 测试类型 | 参数值 | 验证点 |
|----------|--------|--------|
| 低于阈值 | 阈值 - epsilon | 不触发预期行为 |
| 等于阈值 | 阈值 | 触发预期行为 |
| 高于阈值 | 阈值 + epsilon | 触发预期行为 |

### 多阈值联动测试

针对存在业务关联的阈值组合，设计联动测试用例：

**测试方法**：
1. 梳理阈值关联关系，列出联动阈值组
2. 设计多组阈值组合，覆盖「最低阈值、推荐阈值、最高阈值」排列组合
3. 同一测试集下，测试不同阈值组合的系统表现
4. 验证：找到全局最优阈值组合，兼顾性能、成本、准确率

### 阈值敏感性分析

**测试方法**：
1. 以当前设定值为基准，按+/-5%、+/-10%、+/-20%梯度调整阈值
2. 测试不同梯度下，核心业务指标的变化幅度
3. 输出阈值敏感性报告，明确阈值的安全波动区间

**判断标准**：
| 变化幅度 | 判断 | 建议 |
|----------|------|------|
| < 5% | 安全区间 | 阈值在此区间稳定 |
| 5%-15% | 敏感区间 | 需谨慎调整 |
| > 15% | 高度敏感 | 波动风险大，需固定值 |

## Metrics Validation Methodology

### 指标分类

| 指标类型 | 示例 | 验证方法 | 统计要求 |
|----------|------|----------|----------|
| 核心功能准确率 | 意图分类准确率92% | 人工标注测试集>=100条 | 95%置信区间 |
| 性能优化类 | LLM调用减少60%、Token降低45% | 基准组vs优化组对照测试 | 统计显著性p<0.05 |
| 多轮任务类 | 任务完成率90% | 标注多轮任务>=50个完整任务 | 双人交叉标注Kappa>=0.8 |
| 质量安全类 | 幻觉率<=5%、注入拦截率100% | 幻觉测试集>=50条、对抗集>=30条 | 全量测试无漏判 |

### 验证流程

1. **构建测试数据集**
   - 准确率类：100+人工标注样本，正负样本比例匹配生产
   - 减少类：基准场景与优化场景对比，相同100条对话
   - 降低类：相同对话的成本记录对比

2. **执行测试**
   - 运行系统处理测试数据
   - 记录每个指标的实测值

3. **计算与对比**
   - 准确率 = 正确数 / 总样本数
   - 减少比例 = (基准 - 优化) / 基准
   - 降低比例 = (基准 - 优化) / 基准

4. **判断达标**
   - 实测值 >= 声称值 -> 达标，可用于简历
   - 实测值 < 声称值 -> 不达标，需修改简历或优化系统

## Common Test Scenarios

### 全流程测试场景

| 场景 | 输入 | 验证节点 | 预期输出 |
|------|------|----------|----------|

## Interview Q&A

### 基础问题

**Q：怎么验证准确率90%这个指标？**

A：构建100+人工标注测试集，运行系统预测，计算正确预测数除以总样本数。实测值>=90%才能写在简历上。

**Q：阈值30%、50%、75%是怎么确定的？**

A：先根据业务特点设定初始值，然后做边界值测试，观察系统在不同阈值下的行为，微调到最优值。同时做阈值敏感性分析，确保阈值安全波动区间。

### 深挖问题

**Q：Agent测试和传统后端测试最大的区别是什么？**

A：传统后端是确定性系统，输入输出有固定预期；而Agent是LLM驱动的非确定性系统，存在输出波动、幻觉、上下文依赖。我的解决方法：1. 分层测试，确定性模块和非确定性模块分开测；2. 对非确定性模块用统计性测试替代固定预期，大样本保证置信度；3. 多轮对话设计任务完成率量化标准；4. 增加鲁棒性测试覆盖歧义、异常输入。

**Q：怎么测试Agent的幻觉？怎么量化幻觉率？**

A：分三步：1. 构建三类幻觉测试集（事实性、上下文依赖、工具校验），每类>=20条，标注正确答案；2. 每条输入重复跑3次排除随机波动；3. 幻觉率=出现幻觉样本数/总样本数，幻觉判定标准为编造事实、错误引用上下文、工具结果与输出不符。简历声称的是严重幻觉率<=5%，轻微格式问题不计入。

**Q：LLM调用减少60%怎么测出来的？**

A：严格对照测试：1. 构建100条真实对话覆盖核心场景；2. 同一批对话分别跑无缓存基线版本和带双层缓存优化版本，其他参数一致；3. 减少比例=(基线-优化)/基线*100%；4. 整个测试重复3次取平均值，最终稳定数据62%，简历写60%预留安全边际。

**Q：多轮对话任务完成率怎么定义和量化？**

A：先做分级定义：完全完成（核心需求全部满足）、部分完成（有遗漏但无错误）、未完成（有事实错误或中断）。构建50个真实多轮任务，双人交叉标注完成度，统计完全完成占比即任务完成率，实测90%。

### 压力面深挖问答

**Q：测试时LLM的temperature设多少？温度太高怎么保证数据可信度？**

A：测试时全程固定temperature=0，top_p=1，完全关闭LLM随机性，保证相同输入输出一致；对于鲁棒性场景，单独设置temperature=0.7做专项测试，单条用例重复5次，用统计结果保证可信度，全程遵循单变量原则。

**Q：测试集和生产环境数据分布不一样，怎么保证简历指标生产也能达标？**

A：测试集基于线上真实用户日志构建，100条样本匹配生产意图分布、句式分布、场景分布，加入20%OOD样本验证泛化能力；简历指标是测试集最低稳定值而非单次最优值，预留安全边际。

**Q：对照测试怎么排除网络波动、LLM服务波动的干扰？**

A：保证三个不变：LLM模型参数不变、测试用例执行顺序不变、测试环境网络环境不变；同一组测试在同一时间段连续执行3次取平均值，排除临时波动影响，唯一变量就是优化点本身。

**Q：阈值调优后缓存命中率提升但准确率下降，怎么平衡？**

A：做阈值联动测试，遍历缓存相似度阈值和意图置信度阈值组合，绘制准确率-命中率曲线，找到全局最优解：保证意图识别准确率>=90%底线前提下，最大化缓存命中率；绝不为性能指标牺牲核心功能准确性。

**Q：你的系统上线后，怎么保证可用性？有没有做可观测性？**

A：我有完整的可观测性体系：1. 核心指标全量埋点（意图分布、缓存命中率、LLM调用耗时、Token消耗、异常报错数）；2. 配置了告警规则（LLM调用失败率>5%、响应超时>5s、幻觉率突增都会触发告警）；3. 出问题能第一时间发现，而不是等用户反馈。

**Q：如果LLM服务挂了，你的系统怎么办？**

A：我有降级容灾机制：1. LLM不可用时，返回友好提示「服务暂时繁忙，请稍后再试」，不暴露内部错误；2. 本地缓存的历史行程仍可查看；3. 基础对话功能降级运行，保证用户不会看到空白页或报错。

**Q：你怎么上线的？有没有灰度验证？**

A：我采用灰度放量策略：1. 先切5%用户流量，观察24小时，验证核心指标与离线测试一致；2. 然后10%->20%->50%逐步放量；3. 制定回滚方案，出问题5分钟内可回滚；4. 绝不全量切流量，避免全量出问题无法挽回。
